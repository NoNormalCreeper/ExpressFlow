# Stage 3 工程化补充说明

## 本次补充优化

### 1. 在线客户端数量限制

Stage 3 服务端仍采用“一连接一线程”的简单模型。该模型容易理解，适合课程演示，但如果客户端无限连接，会导致线程数量增长并增加服务器压力。

本次在服务端增加最大在线连接数限制。超过上限时，服务端返回 `ServerBusy` 并关闭新连接。

该方案只是轻量保护，不是高并发最终方案。更完整的做法是使用 `select` / `poll` / `epoll` 管理大量 socket，再配合固定大小线程池处理业务请求。

### 2. 单账号单会话

原实现允许同一用户在多个客户端同时登录。虽然业务分发层有全局锁，可以避免文件同时写入导致的数据损坏，但它不能完全解决同一账号多端同时操作带来的业务一致性问题。

本次将会话管理调整为单账号单活动会话。相同角色和用户名再次登录时，旧 token 自动失效。这样可以减少同一账号在多个客户端同时寄件、签收或揽收带来的状态冲突。

该方案仍属于课程项目中的简化方案。更完整的工程方案可以加入记录版本号、乐观锁或数据库事务。

### 3. 客户端断线重连

原客户端在 socket 断开后会直接退出。网络程序不能假设连接一直稳定。

本次在请求发送或接收失败后增加有限次数重连。重连成功后清空本地登录态，并提示用户重新登录后重试。

这里没有自动重发刚才的业务请求，因为寄件、扣款、签收等操作可能已经在服务端执行，只是响应丢失。自动重试可能造成重复操作。

### 4. 协议消息长度限制

原 `receiveLine()` 会一直读取到换行符。如果异常客户端持续发送无换行数据，服务端内存可能被占用。

本次为单行协议增加 8192 字节上限。超过上限时关闭连接，避免异常输入长期占用资源。

## 仍然存在的工程化边界

- 当前服务端仍是一连接一线程，适合演示，不适合大量长连接。
- 当前业务层使用全局业务锁，保证简单一致性，但并发吞吐量较低。
- 当前文件存储没有事务能力，跨多个文件的操作无法做到数据库级原子提交。
- 当前 token 只保存在内存中，服务端重启后所有登录态都会失效。
- 当前 token 没有过期时间，真实系统应增加超时和退出清理策略。
- 当前协议是自定义文本协议，简单可读，但缺少正式协议版本、请求 ID 和幂等控制。
- 当前客户端重连后要求重新登录，没有实现自动恢复会话。
- 当前错误处理主要返回中文提示和简单错误码，没有统一日志系统。
- 当前服务端没有访问日志、限流统计、监控指标和审计记录。
- 当前密码以明文保存在文件中，只适合课程演示，真实系统应使用加盐哈希。
- 当前只有单进程服务端。如果部署多个服务端实例，内存会话和文件存储都需要重新设计。

## 报告中可以采用的表述

本项目 Stage 3 在题目二单机版基础上实现了传统 C/S socket 网络版。客户端和服务端拆分为不同进程，通过自定义文本协议通信。服务端负责 socket 监听、会话管理、请求分发和文件持久化，客户端只负责菜单交互和网络请求。

在验收反馈后，项目补充了几项轻量工程化措施：最大在线连接数限制、单账号单活动会话、客户端有限重连、协议单行长度限制。这些改动没有改变原有业务流程，但增强了网络版在异常连接、重复登录和资源占用方面的防护。

由于课程项目重点是面向对象设计、文件持久化和 socket 通信，当前没有引入数据库、线程池、epoll 或完整事务机制。报告中将这些作为后续优化方向说明，而不是在提交前进行大范围重构。
